## Who sees what

Settings is grouped into three sections. Each item is shown only to a member
whose role carries the matching permission flag (see [Roles](#roles-and-members-c4)).

| Section       | Items                                                                                 |
| ------------- | ------------------------------------------------------------------------------------- |
| **User**      | `Profile`, `Experience`, `Accounts` (`Emails`, `Calendars`)                           |
| **Workspace** | `General`, `Data model`, `Layout`, `Members`, `Billing`, `MCP & APIs`, `Apps`, `Syna` |
| **Other**     | `Admin Panel`, `Community`, `Support`, `Documentation`, `Logout`                      |

`Admin Panel` is shown only to users with the full-admin capability
(`canAccessFullAdminPanel` / `canImpersonate`). `Billing` additionally requires
billing to be enabled on the instance.

## Provisioning (M1)

The production image bundles the A2E apps. Building the image compiles each
app's tarball into `packages/twenty-apps/dist`; the container entrypoint then
registers and installs them on every boot, so a fresh deployment does not need a
manual `app:publish` + `app:install` ritual.

The boot sequence in `entrypoint.sh`, after the database is migrated, is:

1. `command:prod app:provision-bundled`
2. `command:prod install-pre-installed-apps`
3. `command:prod cron:register:all`

### `app:provision-bundled`

Reads every `*.tgz` in `BUNDLED_APPS_DIR` (default
`/app/packages/twenty-apps/dist`) and registers it as an application with
source type `BUNDLED`, `isPreInstalled=true`, `isListed=true` and
`ownerWorkspaceId=null`. The command is idempotent: a tarball already
registered at the same version is skipped, and a newer bundled version updates
the existing registration's `latestAvailableVersion`. Two options are
available:

- `--dir <path>` — read tarballs from a directory instead of `BUNDLED_APPS_DIR`.
- `--dry-run` — log the register/update decisions without writing.

On a non-Docker server the directory is absent and the command logs and skips.

### `install-pre-installed-apps`

Walks every provisioned workspace and installs each registration flagged
`isPreInstalled` through the normal install service. It is idempotent: an app
already installed at the same version is a no-op, and a newer registered
version is applied as an upgrade. A failure on one app is logged and does not
block the others. On a **later** image, a newer bundled version is registered
first, then this pass upgrades workspaces that already run the app.

### Opting out

- `DISABLE_BUNDLED_APP_PROVISIONING=true` skips both commands on a container.
- Shipped worker definitions set that flag, because provisioning must run once
  per boot in the container that owns migrations.
- A container started with `DISABLE_DB_MIGRATIONS=true` skips provisioning too,
  unless `DISABLE_BUNDLED_APP_PROVISIONING=false` forces it (for deployments
  that migrate out of band).

The boot contract is covered by a repository test that runs the real
`entrypoint.sh` with stubbed `yarn`. Running the image/Coolify path on a live
host is a deployment step, **Pending (environment)** — follow `DEPLOY.md`.

## Install, upgrade and uninstall (C3)

### Install an app later

Open **Settings → Workspace → Apps** (page title **Applications**). The page has
a **Marketplace** tab, an **Installed** tab and — with the appropriate
permission — a **Developer** tab, plus an **A2E Suite** section whose header
reads **The all-in-one workspace modules built into this suite. Install only
what you need.**

Each available app appears as a card tagged **Part of A2E Suite** with an
**Install** button. A card can instead state **Not registered on this server**
or **Incompatible server version**; those are readiness states, not UI errors.
Installing an app later augments the current workspace without resetting its
preset and without re-onboarding.

### Hide is not uninstall

Hiding an app is a navigation preference, not an app action: open the edit side
panel on the app's sidebar row and use **Remove from sidebar** (see
[Getting started](/user-guide/a2e-suite/getting-started)). The app keeps its
data and keeps running. There is no "pause with guaranteed restore" mode.

Uninstall is a different, destructive action. From the app's page, **Uninstall**
opens **Uninstall Application?**, whose subtitle says its own contract:

> Uninstalling permanently deletes this application and its records.
> Reinstalling will not restore deleted data.
> To keep your data but stop seeing this app, remove it from your navigation
> instead.

### The uninstall data policy

Starting the uninstall opens a C3 preflight that reports **Checking what will be
deleted...** and then lists, under **Will be deleted:**, every app-owned object,
the record count per object (`N records — <object>`), each app-owned field and
view on standard objects, and any **&lt;app&gt; depends on: &lt;dependency&gt;**
cross-app dependent. You must type `"yes"` to confirm.

The server refuses the uninstall while that destruction is unsafe:

- If any app-owned object still holds records, the removal is blocked with a
  message naming the objects and telling you to export or delete the records
  first — reinstalling will not restore them.
- If another application depends on it, the removal is blocked naming the
  dependent applications so you can detach or uninstall them first.

There is no supported export/retention path yet, so an app holding data is
refused rather than presented as safe. Standard company, person and task records
survive an uninstall; app-owned fields on standard objects may not. Reinstall
restores supported defaults, never deleted data. Run the full
install → populate → upgrade → export → uninstall → reinstall cycle only on a
disposable workspace. See
[`docs/applications.md`](https://github.com/maxx-abrt/A2E-Suite/blob/main/docs/applications.md) for the layer-by-layer troubleshooting table.

### Upgrades

An app with a **newer** available version shows an **Update** tag and the button
**Upgrade to &lt;version&gt;**. That in-app upgrade button is offered for
`npm` and `tarball` source types. Bundled A2E apps do not use it: they are
updated by deploying a newer image, whose startup provisioning registers the
new version and the pre-installed install pass upgrades the workspaces that
already run it. Version compatibility is checked before applying, so an app can
report **Incompatible server version** instead of installing.

## Roles and members (C4)

Member and role management lives under **Settings → Workspace → Members**, which
has three tabs: **Team**, **Invite** and **Roles**. The **Roles** tab appears
only with the **Roles** permission flag.

- **Team** — the workspace member list (**Manage Members**), search, and member
  actions.
- **Invite** — **Invite by link** and **Invite by email**, plus **Approved
  Domains**. Invitations land in this workspace and its configured member
  identity.
- **Roles** — the full role list.

Every workspace ships with two roles:

- **Admin** — a system-managed role (`isEditable=false`). It carries all
  settings access and all record permissions (read, update, soft-delete,
  destroy) and can be assigned to users and API keys. It cannot be edited or
  deleted; for "an Admin but without X", create a new role.
- **Member** — the workspace default role assigned to new members.

The **Roles** tab lists **All roles** (**Assign roles to specify access
permissions**), with **Create Role** to add a custom role. Opening a role shows
three tabs:

- **Permissions** — settings permission flags and per-object record
  permissions. Flags include **MCP & APIs**, **Workspace**, **Users**,
  **Roles**, **Data Model**, **Security**, **Workflows**, **SSO Bypass**,
  **Impersonate**, **Applications**, **Layouts**, **Billing** and **AI**.
- **Assignment** — **Applicability**: **Assignable to Workspace Members**,
  **Assignable to Agents**, **Assignable to API Keys**.
- **Settings** — the role name and description, and the **Danger zone**
  (**Delete role**).

Deleting a role requires confirmation: **Delete Role Permanently**, then
**Confirm deletion of &lt;role&gt; role? This cannot be undone. &lt;members,
agents or API keys&gt; will be reassigned to the default role.** The workspace
default role cannot be deleted, neither can a role you are assigned to, and the
admin role cannot be stripped from the last administrator.

## BYOK keys for Syna

Workspace bring-your-own-key providers live under
**Settings → Workspace → Syna → Providers** (page title **AI providers**).

- **Resolution order** — **For every AI request, Syna resolves the workspace key
  first, then the instance AI_PROVIDERS entry, then the built-in catalog.**
- Keys added here belong to this workspace only and are never returned to the
  browser; the billing note states the provider bills the account that owns the
  key and that a workspace key bypasses the instance custom-provider
  entitlement.
- The **Providers** list shows each provider's source badge — **Workspace key**,
  **Instance** or **Catalog** — and a **Configured** / **No key** state, with
  the selected **Default:** and **Fast:** models.
- The provider form has **Provider name**, **API key** (the existing key is shown
  masked), **Base URL**, **Default model** and **Fast model**, with **Test key**,
  **Save** and **Remove key**.
- **OpenAI-compatible endpoint** — **Add OpenAI-compatible provider** connects
  any self-hosted or proxy endpoint that speaks the OpenAI API.

The per-workspace guardrail is the monthly token cap. It is shown under
**Settings → Workspace → Syna → Usage** as **Monthly token cap** — **Metered AI
tokens used this calendar month against the workspace cap.** — with **Tokens
used** and **No cap set** when unset. The cap is stored on the workspace as
`aiMonthlyTokenCap` and is set through the workspace update path under the AI
settings permission; a null or `0` cap means no cap.

With no provider configured there is a zero-AI state: Syna entries stay hidden
and an admin sees a **Connect a provider** link to this page.

## Backups and restore

Backups are a deployment concern and are covered in
[`DEPLOY.md`](https://github.com/maxx-abrt/A2E-Suite/blob/main/DEPLOY.md).
The essentials an admin must not miss:

- Back up **PostgreSQL 16** (hard floor 14) and **Redis 7** configuration; the
  compose files pin `postgres:16` / `redis:7`.
- Take a database-consistent logical backup (`pg_dump`/`pg_restore`); never tar
  a live PostgreSQL data directory.
- Back up the uploaded-file volume together with the database. Local storage is
  keyed by `{workspaceId}/{applicationId}/…`; a database-only backup leaves
  uploads and app tarballs missing.
- Keep `ENCRYPTION_KEY` (and `FALLBACK_ENCRYPTION_KEY` if used) part of the same
  recovery point — encrypted-at-rest rows are unrecoverable without it.
- Restore into an isolated instance first, then verify records, permissions,
  file downloads and worker jobs before trusting the backup.
- `/healthz` is liveness only; `/readyz` checks database and Redis. Inspect
  server and worker logs after an upgrade if a deployment misbehaves.
