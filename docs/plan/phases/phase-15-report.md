## Decision D-M11A-LINK (generic cross-app linking)

**Chosen pattern: an app-owned `a2eLink` junction with morph targets, owned by a new internal app `a2e-links`, reusing the native `MORPH_RELATION` primitive. The native `attachment` file holder is rejected.**

1. **Primitive reused, not forked.** A link is a junction row whose two endpoints are polymorphic. Twenty stores a morph group as **one `MORPH_RELATION` field row per target object, all sharing a single `morphId`**, with the inverse `RELATION` (O2M) on each target — there is no stored target-type discriminator (`field-metadata.entity.ts:48-51`; `resolve-morph-relations-from-flat-field-metadata.util.ts`). App manifests express this: `RelationFieldManifest` carries an optional `morphId` (`packages/twenty-shared/src/application/fieldManifestType.ts:48-64`), with a real precedent in `packages/twenty-apps/public/last-contact` (`src/fields/last-contact-item-message.field.ts`). So `a2eLink` declares, per endpoint group, one `fields/*.field.ts` morph leg per target object plus the inverse O2M on that target.

2. **Ownership: `a2e-links` owns the junction and both inverse fields on every target object** (consumer-owns-both-sides, per the P4.3 precedent `phase-04-report.md:665-686`). Rationale is identical: a morph leg resolves its target object AND inverse field against the workspace maps at install (`from-universal-flat-field-metadata-to-flat-field-metadata.util.ts:73-100`; `computeMorphRelationFlatFieldName`), so only the consumer can declare the inverse on a provider's object without forcing the provider to depend on the consumer. App-contributed fields on foreign objects are a first-class shape (`reconstruct-data-model-manifest.util.spec.ts:164`). The junction also carries app-owned metadata (`label`, `linkType`) so links are self-describing without adding columns to any host object.

3. **Sides shape.** Two morph groups — an `outgoing` group (the record whose page fired "Link…") and an `incoming`/`target` group — each over the declared linkable set, each leg sharing one `morphId`, each with an app-owned inverse O2M on the target object (SET_NULL/CASCADE on delete, matching the `targetCompany` CASCADE in `compute-attachment-standard-flat-field-metadata.util.ts`). A single row holds one FK per group (`source<A>Id` + `target<B>Id`); linking two records of the same object is fine because the two groups are separate (distinctness is enforced per group only — `validate-morph-relation-creation-payload.util.ts:91-105`).

4. **Install order: linkable apps before `a2e-links`.** An unresolved morph target aborts the whole install atomically (`from-universal-flat-field-metadata-to-flat-field-metadata.util.ts:73-100`, the `phase-04:189` "relation target metadata not found" precedent); there is no manifest-level app-dependency field, so order is the caller's responsibility (onboarding installs sequentially in `applicationUniversalIdentifiers` array order). Presets that include `a2e-links` must list each prerequisite app first. Links over core/standard objects (task, note, company, person, opportunity, calendarEvent, dashboard) need no prerequisite — those objects always exist.

5. **Uninstall preflight: consumer before provider, already enforced by C3 — no code change.** `ApplicationUninstallPreflightService.computeCrossAppDependents` (`application-uninstall-preflight.service.ts:55`) / `assertUninstallAllowed` (`:296`) scans every non-owner relation field whose target object belongs to the app being removed and refuses, naming the dependent. Once `a2e-links` contributes inverse fields on a provider's object, uninstalling that provider is refused while `a2e-links` is installed; the operator uninstalls `a2e-links` first (which removes its contributed fields via the app's own deletion inference). The C3 data gate is unchanged: `a2e-links` owns no provider records, and a record deletion cascades its junction rows via the relation `onDelete`.

6. **Backlink computation: from the persisted inverse relation, never a read-time scan.** Because `a2e-links` contributes an inverse O2M on each linkable object, a record page reads its links in both directions through native relation queries (the `document.documents` / `company.people` shape; the linked-docs precedent) — no content/JSON scan. The "Related" panel is the merge of (a) junction rows and (b) M8d mention backlinks. **M8d should persist its mention-derived backlinks into the SAME `a2eLink` junction under a `linkType` discriminator (user-link vs mention)** so the suite has exactly one related store and M8d's "no full-text scan at read" (`PLAN.md:316-318`) holds without a second index; the writer is M8d's save-time mention extraction from BlockNote `MentionInlineContent` props (`MentionInlineContent.tsx:87-103`).

7. **Search-federation reuse point: the core `search` query, via `useObjectRecordSearchRecords` (`SearchDocument`)** — exactly what the existing `SingleRecordPicker` already uses. `searchAppRecords` **cannot create a link**: `AppSearchRecordDTO` exposes only an opaque `path` (+ label/description/imageUrl) with no `objectNameSingular`/`objectMetadataId` (`app-search-record.dto.ts:8-27`), and the front even sets `objectNameSingular: ''`. App-provider groups may be merged for *display* (as `SidePanelSearchRecordsPage` does), but the link-addressable selection must key off `SearchRecordDTO.objectNameSingular` + `recordId` (`search-record.dto.ts:8-38`). The picker UI is the existing `SingleRecordPicker` with `objectNameSingulars` = readable+active+searchable non-system objects (already computed in `LinkToRecordPicker.tsx:38-45`); the only new work is persistence + the Related panel.

8. **Related widget surface: an app `FRONT_COMPONENT` widget inside an app-declared standalone page-layout tab — not a new native widget type.** A new widget *type* is impossible without a host change: `WidgetType` is a closed enum (`WidgetType.ts:1-27`) mirrored in the server enum and the front dispatcher (`WidgetContentRenderer.tsx:29-102`), and `SyncableEntity` has no `PageLayoutWidget` (`syncable-entities.enum.ts:1-17`) — apps ship widgets only nested in a layout/tab they declare (`pageLayoutManifestType.ts:20-27`). The only app-code-backed payload is `FRONT_COMPONENT` (`page-layout-widget-configuration.type.ts:140-144`, rendered by `FrontComponentWidgetRenderer`). Precedents: a2e-documents' `document-page` FRONT_COMPONENT (`document.page-layout.ts:37-45`) and a2e-chat's additive standalone tab on the standard company page (`company-discussions.page-layout-tab.ts:15-35`). Per-direction lists can reuse the native relation/junction widget (`resolveJunctionConfig` / `resolveReverseJunctionConfig`, `getJunctionConfig.ts:116`) — the app junction is wireable via `junctionTargetFieldUniversalIdentifier` (rich-app fixture) — but the **merged bidirectional links+backlinks panel** needs the front component. Consequence: "Related on every record page" means one standalone tab per targeted standard page layout (bounded) plus the app's own record pages; a host-owned universal widget is the only generic injection and is out of scope here.

9. **Rejected alternatives.** (a) *Reuse the native `attachment` holder* — it is the only truly open morph holder (the host auto-provisions an inverse for every object, incl. future/app objects, `object-system-relations-on-create-side-effect-handler.service.ts:28-113`), but it is the FILES widget source (`WidgetTypeToRelationFieldName.ts:8 → attachments`), carries file semantics (`compute-attachment-standard-flat-field-metadata.util.ts:158-210`), and models only "holder→target" with no source endpoint — every link would surface in every record's FILES widget and pollute a host object. Rejected. (b) *Discriminator-pair junction* (`objectMetadataId`+`recordId`, the legacy `timelineActivity` shape) — no referential integrity, no native picker/display, and it is exactly the parallel linking system M11a must not fork. Rejected. (c) *A new host-owned standard morph holder* (add a `linkTarget`-style object to `DEFAULT_RELATIONS_OBJECTS_STANDARD_IDS`, `default-relations-object-standard-ids.constant.ts:3`) — cleanest for truly universal coverage, but a host metadata change (new standard object + an upgrade-command backfill of inverse fields for existing workspaces) outside L-LINK's app-file lane. **Recorded as the fallback** if M11a later needs arbitrary objects the apps do not declare.

10. **Residual limitation (recorded honestly).** Morph targets are static in the manifest, so coverage = the declared linkable object set: `a2eLink` cannot link an undeclared object, and requires the apps owning declared objects to be installed first (point 4). M11a's "all objects" is satisfied for the curated A2E + core set. The **distributed variant** (each linkable app declares its own leg on `a2eLink` sharing the `morphId`, so `a2e-links` ships first and optional apps opt in) would remove the hub prerequisite, but cross-app morph-group assembly is not exercised anywhere today and needs a feasibility probe before it could replace point 2's shape.

11. **Deferred implementation legs (NOT this spike).** M11a-i: scaffold `packages/twenty-apps/internal/a2e-links` with the `a2eLink` object + two morph groups + declared inverse fields + link metadata, and patch/version it. M11a-ii: the universal "Link…" action wiring `SingleRecordPicker` → `useObjectRecordSearchRecords` → `createALink`. M11a-iii: the `FRONT_COMPONENT` Related tab (links + M8d backlinks) with the standard-page-layout tab declarations. M11d (C5 events) and M11e (inbox) remain later.
