## Codebase Patterns (Study These First)

- **Editor capability checks:** the document/note rich-text body is twenty-front's shared BlockNote schema at `packages/twenty-front/src/modules/blocknote-editor/blocks/Schema.ts` (defaultBlockSpecs + custom `callout`/`file` + inline `mention`) — NOT the TipTap `advanced-text-editor` (that one serves forms/AI/email). Any "new editor block" question starts there.
- **Advanced BlockNote adds are license-gated:** `@blocknote/{core,react,mantine}` are MPL-2.0, but `@blocknote/xl-docx-exporter`, `xl-pdf-exporter` and transitive `xl-multi-column` are "GPL-3.0 OR PROPRIETARY" already shipped in `twenty-front` (root AGPL-3.0). Check D07 before wiring more XL packages.
- **`@blocknote/core` cannot be imported under `twenty-front` jest:** its transitive `prosemirror-highlight` ships untransformed ESM and `transformIgnorePatterns` excludes it, so any editor-dependent util must inject the parser (dependency inversion) and keep the BlockNote adapter in a separate, untested module. Pure DOM sanitizers use `jsdom`'s `DOMParser` and are fully testable.
- **Chat realtime fan-out hangs off metadata database events, not a resolver:** app-owned chat CRUD (`chatChannel`/`chatMessage`/`chatReaction`/`chatReadCursor`) is metadata-engine-generated, so publishers attach via `@OnDatabaseBatchEvent('chatMessage', DatabaseEventAction.X)` in `modules/chat/listeners/` and call `RealtimePublisherService.publish(buildChatChannelTopic(...), payload)`. Relations surface as join columns on the raw event row. Subscribe-time ACL stays in `RealtimeTopicAccessService`; publishing is best-effort (never fail the write).
- **Chat relation columns are `${fieldName}Id`, NOT the SDK `joinColumnName`:** the metadata engine derives the workspace column from the relation field name (`chatMessage.channel` → `channelId`, `chatMessage.author` → `authorId`, `chatReadCursor.workspaceMember` → `workspaceMemberId`, `chatReaction.message` → `messageId`), ignoring `manyToOne('customName')` from the app. Server code reading raw DB-event rows or the workspace ORM must use the field-name form; the GraphQL scalar input/output is also `${fieldName}Id`. The committed `ChatRealtimePublisherService` still reads the SDK names (`readCursorChannelId`, `reactionMessageId`, …) and is broken — verified by integration introspection (P5.1-chat-attachments-tests).
- **Native pages for app features are `twenty-front` code, not app code:** an app cannot register a route (phase-04 boundary), so the chat page is a hard-coded route in `modules/app/routing/utils/createWorkspaceRouteObjects.tsx` + an additive `AppPath` member, with the feature module under `src/modules/<feature>/` and a thin `src/pages/<feature>/<Name>Page.tsx`. Channels/messages are app-owned **metadata objects**, so read them with `useFindManyRecords`/`useCreateOneRecord`/`useUpdateOneRecord` (relation scalars `${fieldName}Id`); the two server custom resolvers (`chatMessages`, `chatUnreadCounts`) are `@MetadataResolver()` and must be queried with `useApolloCoreClient()` / `client: apolloCoreClient`, not the default client.
- **oxlint `twenty/matching-state-variable` is strict:** the local binding must equal the state key (`selectedChatChannelIdState` → `selectedChatChannelId` / `setSelectedChatChannelId`), and `useRef` for state trips `twenty/no-state-useref`. Also `twenty-shared/utils` does **not** export `isNonEmptyString` (it is `@sniptt/guards`); only `isDefined` etc. live there.
- **Chat live layer reuses the P2.2/P2.3 primitives verbatim:** `useRealtimeTopic<Event>({ topic: buildChatChannelTopic({ workspaceId, channelId }), enabled, onEvent })` from `~/modules/realtime/hooks/useRealtimeTopic` (note the `~/modules/realtime/*` alias, NOT `@/`), offline sends via `useRealtimeOfflineQueue(CHAT_OFFLINE_QUEUE_NAMESPACE)` (`enqueue` while `status !== 'connected'`, ordered `drain`/`clear` on reconnect), typing via `useWorkspacePresence`/`RealtimeTypingIndicator`. A realtime event fold must be **insert-by-id idempotent** because the page query, the reconnect catch-up and the offline replay can all deliver the same row; and offline queue ordering must tie-break by **insertion order** (two sends land in the same ms), not by uuid.
- **Cmd+K app-provider safety:** `useFindManyRecords` calls `useObjectMetadataItem`, which **throws** for an uninstalled app object — a Cmd+K provider must use `useObjectRecordSearchRecords` (guards with `useDoObjectMetadataItemsExist` + `skip`) or gate on `useDoObjectMetadataItemsExist`. Chat search results join the existing `groupSearchResultItems` pipeline by supplying `groupKey`/`groupHeading`; channel hits deep-link via `getAppPath(AppPath.Discussions, undefined, { channelId })` and `ChatPage` reads the `channelId` query param.
- **Record-linked app features = a native relation-scoped widget type + app metadata, not a new route:** a record-page tab is a page-layout widget whose `getTabsRenderableForTargetObject` mapping (`WIDGET_TYPE_TO_RELATION_FIELD_NAME[type] = '<relationFieldName>'`, plus `WIDGET_TYPES_REQUIRING_RELATION_FIELD`) auto-hides it when the record object lacks that relation — so a tab can ship before the providing app is installed. Adding a new `WidgetType`/`WidgetConfigurationType` is cross-package: shared `WidgetType` + `…-widget-configuration.type.ts` (+ `types/index.ts`), the generated `packages/twenty-front/src/generated-metadata/graphql.ts` (`WidgetType`, `WidgetConfigurationType`, the `WidgetConfiguration` union, a `XxxConfiguration` object type), the front `WidgetContentRenderer` + `PrerenderablePageLayoutWidgetTypes` + `isViewportFillingWidgetType`, and on the server a `XxxConfigurationDTO`, the `ALL_WIDGET_CONFIGURATION_TYPE_VALIDATOR_BY_…` map (the two validator hashmaps are exhaustive `Record<WidgetType,…>` — they fail typecheck until the new member is added), both `from-…-configuration` switches, `validate-widget-configuration-input.util.ts`, and a `2-39-instance-command-fast-<epoch>-…` `ALTER TYPE "core"."pageLayoutWidget_type_enum"` migration registered in `instance-commands.constant.ts`.
- **Apps pinned to `twenty-sdk` 2.31 can still declare 2.39 features via string literals + a widened config:** `PageLayoutWidgetManifest.type` is `string` in 2.31, but `configuration.configurationType` is a closed union, so a new widget type is written `type: 'DISCUSSIONS'` + `configuration: { configurationType: 'DISCUSSIONS' } as unknown as PageLayoutWidgetUniversalConfiguration`. A company tab is added additively with `definePageLayoutTab` (`pageLayoutUniversalIdentifier: STANDARD_PAGE_LAYOUT.companyRecordPage.universalIdentifier`, exported from `twenty-sdk/define`) instead of shipping an app page layout, which would override every default company tab. `WidgetType` is NOT exported from 2.31 `twenty-sdk/define`.
- **Core-schema native feature surface = `@CoreResolver()` + hand-written gql + local types:** a core entity's inbox/resolver (e.g. `notification`) is not in the metadata codegen surface, so the front writes its own `gql` document + result type (chat-unread-counts / document-share precedent) and queries it with `useApolloCoreClient()` / `client: apolloCoreClient`. On the server, `@CoreResolver()` is mandatory (else the endpoint silently 404s at the schema level) and oxlint `twenty/graphql-resolvers-should-be-guarded` **requires an explicit permission guard** — use `@UseGuards(WorkspaceAuthGuard, UserAuthGuard, NoPermissionGuard)` for caller-scoped own-data resolvers (two-factor-auth precedent), `WorkspaceAuthGuard`+`UserAuthGuard` alone fails lint. A core `*.entity.ts` and its `*.dto.ts` may share the same `@ObjectType('X')` name (document-share does exactly this) — the DTO carries the `@Field`s, the entity has none.
- **Inbox realtime fan-out hangs off the custom dispatch listener, not a DB event:** `notification` is a core-schema entity (no metadata DB events), so `NotificationRealtimePublisherService` is called from `NotificationRequestedListener` with the `inboxNotifications` returned by `NotificationService.dispatchNotifications`. The gateway grammar/parser and the user-scoped subscribe ACL for `workspace:<id>:inbox:<userId>` already existed (P2.1) — a slice only needs `buildInboxTopic` + a payload builder. Badge counts must be read back through `NotificationService.countUnread` (same rows the inbox list queries), never a parallel counter. Note: read/archive-side badge decrement is NOT wired (no resolver calls `markAsRead`/`archiveNotification` until P8.2); publishing from `NotificationService` itself would need a forwardRef because the publisher depends on it.
- **Mentions are one parser + one producer, per-surface listeners:** `packages/twenty-server/src/modules/mention/` owns `parseMentions({surface, body})` (chat `@[label](workspaceMemberId)`; BlockNote document `content`; BlockNote comment `comments`) and `MentionNotificationService.notifyMentions({source, body, excludeWorkspaceMemberIds})`, which resolves member→user, filters through `MentionAccessService` (P2.1 `RealtimeTopicAccessService` record/channel ACL with an explicit member identity) and emits one `MENTION` request per permitted user. Surfaces stay thin: `ChatMentionService` maps a message to `{surface:'chat',channelId,messageId}`, and `DocumentMentionListener`/`DocumentCommentMentionListener` diff against `before` so an edit does not re-notify (documents diff mention ids, comments diff comment ids). Payload always carries `snippet` + deep-link ids (`chat.mention` → channelId/messageId; document/comment → `{objectNameSingular:'document', recordId}`). Any class injecting a `*WorkspaceService` type trips `twenty/inject-workspace-repository`; add `// oxlint-disable-next-line` directly above `export class`.
- **Home/workspace dashboard widgets extend the P2.4 dock registry via `registerWorkbenchWidget`, not `DEFAULT_WIDGETS`:** `modules/workbench-dock/registry/__tests__/workbenchWidgetRegistry.test.ts` asserts the snapshot is exactly the six defaults, so new widgets are added by a registrar imported for side effects (a new `id`), or by re-registering an existing id with a `Component` to replace its placeholder. Re-registering overrides the map entry and `unregister()` deletes it outright (the default placeholder is not restored), so treat re-registered defaults as permanent. Widgets that compose queries should inject their parser/projection through a pure util (`buildContributionGrid`, `selectMyTasks`, `selectUpcomingEvents`, `summarizeTimelineActivity`) and keep the hook container thin — this is what keeps them Tier-0 testable. `useFindManyRecords` filter operands are `eq`/`neq`/`gte` (not `ne`), relation scalars are `${fieldName}Id` (`assigneeId`, `workspaceMemberId`), standard task "done" status value is `'DONE'`, and `calendarEvent` is UI-read-only but queryable (`startsAt`, `isCanceled`).
- **Email notifications reuse `EmailService.send` + `renderEmail`, never a parallel mailing path:** `EmailService.send` only enqueues a nodemailer job, so a sender resolves the recipient, renders a `twenty-emails` template twice (`renderEmail(template,{pretty:true})` for html + `renderEmail(template,{plainText:true})` for text — billing-reminder precedent), and sends. The P8.1 `NotificationService.dispatchNotifications` already returns `emailDigestBatches` filtered by per-type channel preference and quiet hours, so the email service stays a thin renderer over that contract (single quiet-hours/preference implementation). Lingui gotcha: under `@lingui/swc-plugin` (twenty-server jest transform) `msg\`text\`` compiles to a **hashed** id (`00RL+v`), so specs must compare against `msg\`text\`` descriptors (or assert `.message`, retained because `stripNonEssentialFields: false`) — never the literal text on `.id`; and a mocked `I18nService.getI18nInstance` must resolve `descriptor.message ?? descriptor.id`.
- **Workspace file browsing + trash reuse existing primitives, never a new store or endpoint:** Drive files are standard `attachment` rows extended by the app (`folderId`/`starred`/`sourceApp`/`description`/`archivedAt`), folders are the app-owned `driveFolder`; all reads/writes go through `useFindManyRecords`/`useCreateOneRecord`/`useUpdateOneRecord` (relation scalars `${fieldName}Id`, e.g. `folderId`/`parentId`). Trash is a shared additive `archivedAt` DATE_TIME on both objects + one `lib/drive-trash-retention.ts` (unparsable timestamp never purges) consumed by BOTH the nightly app logic-function cron (`0 3 * * *`, generated plural delete with a required `filter: { id: { eq } }`) and the front UI predicates — mirror P3/P4.3, never a second retention scheme. The page is a hard-coded front route (`AppPath.Drive` + lazy `createWorkspaceRouteObjects` entry + `pages/drive/DrivePage.tsx` + `modules/drive/`), and the client-side folder tree must be cycle-safe on its own (assemble roots from the flat `parentId` map, promote leftover components) because the server guard only repairs corruption after the fact.
- **A metadata-only `a2e-*` app scaffold is an independent Yarn package with its own UUID block:** app dirs are NOT root workspaces — copy the closest app's `package.json`/`tsconfig`/`.yarnrc.yml` (`nodeLinker: node-modules`)/`.oxlintrc.json`/`.nvmrc`, claim the next free `c31X*` namespace (a=Documents, b=Projects, c=Chat, d=Drive), and commit fresh application+role UUIDs (`node -e "crypto.randomUUID()"`). `yarn install` resolves from the global cache (`~/.yarn/berry/cache`) when the lockfile matches a sibling's; gates are `npx tsc --noEmit` (or `yarn typecheck`), `yarn lint` (plain oxlint 0.16.12 — no `--type-aware`), `node --test --experimental-strip-types src/**/__tests__/*.test.ts`, `npx twenty dev:build .` (writes `.twenty/output/manifest.json`, runs an internal typecheck), and `npx oxfmt --check <app-dir>` from the repo root. The 2.31 SDK DOES export `STANDARD_OBJECT_UNIVERSAL_IDENTIFIERS.attachment`, and an app field can extend any standard object (joinColumn `folderId` → workspace scalar `folderId`); an app-defined TABLE view can target a standard object and mix `STANDARD_...fields.name.universalIdentifier` with app fields. The 2.31 page-layout widget set has **no `FIELD_RELATION`** config (use native `FILES` or omit); write the fields-graph integrity test by importing the object/field modules and reading `module.default.config` (no built manifest needed).
