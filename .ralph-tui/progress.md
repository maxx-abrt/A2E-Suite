## Codebase Patterns (Study These First)

- **Cross-app relation pairs are owned by the *consumer* app and make the provider a hard install prerequisite**: when app A wants to show app B's records on its own page, A declares BOTH sides in its manifest — the M2O FK as a standalone `fields/*.field.ts` with `objectUniversalIdentifier` = B's object uid (join column `<name>Id`, `onDelete SET_NULL`), and the O2M inverse on A's object (models: A2E Projects' `document.project` + `project.documents`, A2E Chat's `chatChannel.project` + `project.discussions`). The target object must exist at metadata-sync time (`validate-morph-or-relation-flat-field-metadata.util.ts`), so A cannot install without B; the install fails closed and atomically (no application row, no partial metadata) — that is the C4 "safe degradation" for a required cross-app link. A page-layout `FIELD` widget that names a relation field id therefore can't dangle, but it also can't auto-hide; only widget *types* like `DISCUSSIONS` auto-hide when the owning app is absent. Do not build a front-component fallback for a missing relation — it is unreachable, and install/onboarding partial-failure UX is owned by US-026/US-027.

- **Persisting an app-owned workspace object from `twenty-front`**: the app declares the object (e.g. `documentRevision`, `documentCommentThread`) in `packages/twenty-apps/internal/a2e-documents/src/objects/`, and the front writes it through hand-written `gql` documents + `useApolloCoreClient()` (the objects are absent from checked-in generated metadata — regen with `nx run twenty-front:graphql:generate` once installed). Permissions are the platform's object permissions on the standard GraphQL API; the client adapter must fail closed on a denied transport (no read leak, no write applied), not add a parallel authz layer.
- **Copying note/template body blocks into a fresh record must re-key block anchors**: `remapTemplateBlockIds` (`a2e-documents/src/lib/instantiate-template.ts`) is the single anchor re-key authority (fresh ids, internal refs followed, `threadId` untouched, malformed/non-array refused). Reusing it — rather than parsing/copying raw blocknote — is what keeps a copy from aliasing the source's comment/thread state. `createBlockId` is injectable for deterministic tests; note-copy passes it through `buildNoteCopyBlocks`/`buildRecordNoteCopyContent`/`buildRecordNoteCopyPayload`.
- **Server-side compare-and-set for an app-owned record is a post-commit repair, not a reject**: the app SDK exposes only `databaseEventTriggerSettings` (no pre-write hook), so a `*.updated` logic function reads `properties.before`/`after` (full records) and restores the winner. The expected value must ride on the write itself as an additive field (here `document.contentRevision` head token + `contentBaseRevision` expected token); a repair write uses a `repair-` sentinel base so it is never itself re-classified (loop termination). Writers that omit the token stay last-write-wins (single-writer guidance). The pure decision lives in `a2e-documents/src/lib/document-revision-cas.ts` with an injected-free signature so `node --test` covers it without a server.
- **a2e-projects task status has TWO fields — pick deliberately**: the standard Twenty task already ships a `status` SELECT (TODO/IN_PROGRESS/DONE, and a native `byStatus` kanban), and the app adds a parallel `projectStatus` SELECT with the same values. The board (`task-board.view.ts`), `project-tasks.view.ts`, the calendar (`task-calendar.view.ts`, status column + DONE exclusion) and all three My-tasks smart lists (`my-tasks.view.ts`, `created-by-me.view.ts`, `overdue-tasks.view.ts` — status column + DONE exclusion) are wired to `projectStatus`; `current-tasks.view.ts` and the native record tasks tab still read the standard `status`. Read code paths go through `lib/task-status.ts` (`readTaskPipelineStatus`: projectStatus authoritative, standard status fallback, unknown → null). Reconcile which field a surface should read before adding any status logic (C5) — do not add a third status or a sync workflow. A view cannot express the read-time fallback, so a surface must choose one field for its filter/column: the pipeline field is correct once the app writes it (native status keeps its TODO default).
- **An a2e-projects project page is ONE page-layout; a PLAN "tab" name can already be a widget inside an existing tab**: `page-layouts/project.page-layout.ts` is the single `RECORD_PAGE` for `project`, and the P4.2 gantt "tab" is the `Gantt` `FRONT_COMPONENT` widget inside the `Timeline` tab (README-documented), not a separate tab — the tab set is Accueil/Timeline/Tâches/Tableau/Fichiers/Documents/Discussions. Tabs reuse native primitives (`RECORD_TABLE` + `viewUniversalIdentifier` for tables/kanban, `FILES`, `FIELD` for a relation). Before adding a tab for a PLAN bullet, audit the existing layout and `project-object-integrity.test.ts`'s tab-set test: adding a duplicate Gantt tab is a duplicate system, not a completion. The `c31b0200-0009-*`/`000a-*` namespaces are tab/widget ids; keep them additive.

- **Native CSV/bulk import-export is entirely client-side in `twenty-front`; there is no server import engine**: the wizard (`spreadsheet-import/`) validates per row into `__errors` and submits only valid rows via `useOpenObjectRecordsSpreadsheetImportDialog` → `buildRecordFromImportedStructuredRow` → `useBatchCreateManyRecords({ upsert: true })` (generic `createMany`); export is browser-side `generateCsv` in `useRecordIndexExportRecords.ts` (`json-2-csv` + `sanitizeValueForCSVExport`), and `IMPORT_CSV`/`EXPORT_CSV` only gate the command-menu items. So "reusing native import" for tasks means this generic pipeline — do not add a server import module or an `a2e-projects` CSV engine. Server batches are atomic, so partial-failure feedback is per-batch: `spreadsheetImportFeedback.ts` (`partitionRowsByValidationErrors` / `partitionRowsByImportResult`) is the single feedback seam, and the committed count is read from the shared `spreadsheetImportCreatedRecordsProgressState` atom — not a `useRef`, which the custom `twenty(no-state-useref)` rule rejects for state.

- **Assistant context mapping reads the app-declared input schema straight from the front metadata store — no extra registry/GraphQL call and no server change**: `logicFunctionsSelector` returns `LogicFunction.toolTriggerSettings.inputSchema` (populated by `FindManyLogicFunctions`), so `getContextToolButtons` offers the union of (a) the context object's owning-app tools and (b) any installed app's read-only tool whose schema references the context object — a `<objectNameSingular>Id|Ids|Uid|Uids` property or an `objectUniversalIdentifier`, walked through `properties`/`items`/`additionalProperties`. This makes a cross-app tool (a2e-projects' `extract-tasks-from-document` requiring `documentId`) surface on a `document` page. `AiChatEmptyState` is mounted once inside `AiChatEditorSection`, so the side-panel assistant and the full `AiChatPage` render the same context buttons and suggested prompts — do not add a second full-page shell or a parallel tool list.
- **P9.1 streaming / model-provider config / AI usage-logging are native and already wired — reuse them; do not add a transport or a per-tool-call billing event**: the assistant streams over the existing SSE client (`twenty-front` `sseClientState` → `useAgentChatSubscription` graphql-sse) fed by the server `AgentChatEventPublisherService` Redis chunk list; provider config comes from the existing AI settings via `AiModelRegistryService` (`chat-execution.service.ts` reads `workspace.smartModel` + validates/resolves the model); usage is logged to event-logs through `AiBillingService.emitAiTokenUsageEvent` → `UsageRecorderService.record` → `WorkspaceEventEmitter` `USAGE_RECORDED` → `UsageEventListener` → `usageEvent` envelope (gated by `EventLogEmitterService.isEnabled()`). App-tool calls are audited separately as `Logic Function Executed` with LOGIC_FUNCTION credit billing — not a second AI event. The only missing acceptance was test coverage of the AI billing → usage-log write, so `ai-billing.service.spec.ts` wires the real `UsageRecorderService` and asserts the emitted `USAGE_RECORDED` batch; a future P9.1 change needs neither a new transport nor a per-tool billing enum.
- **Read-only app AI "actions" are logic functions with `toolTriggerSettings`, surfaced on a record page by a `<objectNameSingular>Id` input property — and they must reuse the one authorized read path, never fork a second read**: in `a2e-documents`, `summarize-document` / `translate-document` / `improve-document-writing` each declare a `documentId` (translate also requires `targetLanguage`), so `getContextToolButtons.toolInputSchemaReferencesObject` (US-040) offers them as read-only buttons on a `document` page. All three delegate to `runDocumentAction` → `readDocumentContent` (US-013, the single caller-scoped read); the assistant owns the LLM transformation, so an action tool returns caller-authorized content + its validated options, never a generated result and never a write (C6). Add an action by adding one thin `defineLogicFunction` + its universal id; do not add `registerAiTools`, a table, or a per-action read/query. Validate the action's own options BEFORE the read so a bad option fails closed without touching the document (`INVALID_INPUT`), and keep missing/unauthorized as one typed `DOCUMENT_NOT_FOUND` with null body/metadata.
- **A generic (non-app) AI contract belongs in `twenty-shared/src/ai`, not in an app's `src/lib`**: the barrel (`src/ai/index.ts`) is auto-generated by `packages/twenty-shared/scripts/generateBarrels.ts` (`npx nx run twenty-shared:generateBarrels`; `nx build twenty-shared` also runs it), types go in `src/ai/types/*.type.ts` and pure functions in `src/ai/utils/*.util.ts` (jest `__tests__/*.spec.ts`, imported via the `@/ai/...` alias). The app `a2e-accounting` `aiCacheEntry` object / `buildAiCacheKey` is the P7-gated Bilan pattern to *mirror*, not the home of a shared contract — importing `twenty-shared` from an app logic function is lint-blocked, so app-side wiring of a shared contract is front/server-only. When a story says "generic cache contract only", do not touch the app object.
- **Private AI results are cached under a `workspace + access` key; only a reviewed public-catalogue result may be global**: the cache key resolves to `scoped|workspace:<id>|access:<accessScopeId>|kind:…|model:…|data:…|catalogue:…|payload:…` for anything private (or public-but-unreviewed) and `global|…` only when `visibility === 'PUBLIC_CATALOGUE' && reviewedForGlobalSharing === true`. `accessScopeId = buildAccessScopeId({ roleUniversalIdentifier, permissionFingerprint })`, so a role swap or a grant edit changes the key and a private entry can never be read across workspaces (C6). Reuse additionally requires matching model/data/catalogue versions and an unexpired entry; a malformed `expiresAt` fails closed. `evaluateAiResultReuse` returns a typed reason (`FRESH`/`KEY_MISMATCH`/`NOT_REVIEWED`/`EXPIRED`/`VERSION_MISMATCH`/`ACCESS_CHANGED`) so callers never have to re-derive the decision.
