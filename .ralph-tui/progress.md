- **Host "app landing" pages** follow `HomeDashboard`/`InboxPage`: a `~/pages/<x>` component (`~` = `src`), registered in `createWorkspaceRouteObjects.tsx` with a new `AppPath`, a `title-utils.ts` case, and self-gating via `useIsDocumentApplicationInstalled` / `hasObjectMetadataItem`. The app-side nav row then points at it with a `NavigationMenuItemType.LINK` (VIEW→LINK like US-101); the link must be added to `INTERNAL_NAVIGATION_MENU_ITEM_ROUTE_PATHS` (twenty-shared) and both `twenty-shared` and `twenty-sdk` dist rebuilt.
- **Template gallery entry seam**: every surface opens via `useOpenTemplateGallery({ category, templateKey })`; category + key are *soft* preselects in jotai atoms (`templateGallery*PreselectState`) read by `TemplateGallerySidePanelPage` → `TemplateGallery(initialCategory, initialTemplateKey)`. App front-components cannot use it (isolated runtime) — landing pages that deep-link the gallery must be host pages.
- **Two shapes of "landing"**: (1) a *new* host route (`~/pages/<x>` + `createWorkspaceRouteObjects` + `AppPath` + `title-utils` + nav row repoint), as with Bureau `/bureau`; or (2) an *existing* host page enriched in place when a nav row already targets it (Agenda `/calendar`), as with US-151 — default the host to the intended surface and prepend a self-contained header component that takes the host's own action as a callback, so the host keeps a single write path and no second route/nav is added.
- **`twenty(max-consts-per-file)`**: max one exported `const` per file. Split paired constants into separate files (see `BureauLandingTemplateCategory.ts` vs `BureauLandingTemplates.ts`); `styled` consts are exempt.
- **Pre-existing red**: `usePageChangeEffectNavigateLocation.test.ts` "tests should be exhaustive" was red at HEAD because `AppPath.{Drive,Calendar,Discussions,Inbox}` lack matrix rows; `UNTESTED_APP_PATHS` is the exemption list.
- **Custom Cmd+K group + install-gated host commands**: the Cmd+K root (`SidePanelCommandMenuItemDisplayPage`) renders metadata-engine items into the fixed `Pinned`/`Other`/`Fallback` groups and appends a few hardcoded host commands to `Other`. A *new named group* (e.g. `Create…`) is a sibling `<SidePanelGroup heading={t\`…\`}>`; its command ids must also be spread into `selectableItemIds` and counted in `hasNoMatchingItems`, or keyboard nav/search break. Host commands that call a hook reading a foreign object's metadata (`useCreateOneRecord` on an app object) must be **split into outer/inner components** and only mounted when the owning app is installed — `useObjectMetadataItem` throws (not returns null) for a missing object, so an unguarded hook crashes the menu.
- **Landing without an app object (Syna/Agenda)**: when the surface is a *host* feature (no `Application`/object metadata to install-gate on), mount the landing as an *empty-state* enrichment of the existing host page rather than a new route — for Syna that is `AiChatEmptyState`, gated on `AiChatSurfaceContext === AI_CHAT_SURFACE.PAGE` so the side panel stays compact. No `/syna` `AppPath` is needed. A *new* route is only justified when the landing must own content during an active thread.
- **Cross-app event contract (C5)**: put the vocabulary in `twenty-shared/src/cross-app-events/` (family/action types + `computeCrossAppEventName` + `buildCrossAppEventPayload` + `isCrossAppEventPayload`); the barrel + `package.json`/`project.json` entries for a new shared submodule are auto-generated by `npx tsx packages/twenty-shared/scripts/generateBarrels.ts` (or `nx build twenty-shared`), do not hand-edit `index.ts`. Server side reuses the existing primitives only: a `@OnDatabaseBatchEvent('*', <dbAction>)` listener delegates to a pure mapper, then publishes on one custom channel via `WorkspaceEventEmitter.emitCustomBatchEvent` (gated by `WorkspaceCacheService.getOrRecompute(workspaceId, ['flatApplicationMaps']).flatApplicationMaps.idByUniversalIdentifier`). `isNonEmptyString` is from `@sniptt/guards`, NOT `twenty-shared/utils`.
- **Extending the C5 contract with a family** is additive and needs four edits: the `CrossAppEventObjectFamily` union, `CROSS_APP_EVENT_OBJECT_FAMILIES`, `CROSS_APP_EVENT_OBJECT_NAME_BY_FAMILY` (family→object singular) and `CROSS_APP_EVENT_ACTIVATION_APP_BY_FAMILY` (only for optional-app objects). The generic `@OnDatabaseBatchEvent('*')` projector then emits `<family>.<action>` for that object automatically — no mapper change needed. Build `twenty-shared` before the server can consume it. Caveat: the C5 payload snapshot is `after ?? before` only (no `before`, no `updatedFields`), so a contract subscriber cannot diff edits; prefer a source that is already incremental (e.g. the US-139 `documentMention` index rows, one row per mention) to get duplicate-free notifications.
- **Inbox notification primitives (P8)**: producers call `NotificationService.requestNotifications({ workspaceId, requests: [{ userId, type, payload }] })` (the row's `userId` is the **core** user id, not the workspace-member id); `payload` drives the front (`resolveNotificationDeepLink` reads `{objectNameSingular, recordId}` / chat `channelId` / `calendarEventId`; `getInboxNotificationPreview` reads `preview|snippet|title`). Factories live at `twenty-server/src/engine/core-modules/notification/{notification.requested.listener,notification.watch.service,notification-watch.listener}`. Reuse `MentionNotificationService` (member→user hop + `MentionAccessService` permission filter + `buildMentionNotificationPayload`) rather than re-emitting `MENTION` payloads by hand.
